3. 若存在上述規則，必須落實到系統結構中（不能只寫在描述裡），體現為：必要的工作表 / 業務流程 / 自訂動作 / 自動化工作流 / 統計分析入口

4. 必須覆蓋完整業務閉環：發起 → 處理 → 審批執行 → 結果登記 → 異常處理 → 統計分析

5. 工作表設計不能只停留在"主業務物件"層面，還應判斷是否需要補齊：
   - 基礎資料物件 / 業務單據物件 / 過程明細物件 / 狀態流轉物件 / 庫存臺賬流水物件 / 異常處理物件 / 統計分析支撐物件

6. 不得為控制表數量省略關鍵過程物件、流水物件、異常記錄物件或分析支撐物件。若某業務規則需要額外物件才能成立，優先保證業務閉環。

## 設計原則

- 優先體現"為什麼這樣設計"，而不只是"包含什麼"
- 目標是生成覆蓋**完整業務鏈**的真實可用方案，不因使用者描述簡短就縮減結構，應補齊基礎資料、業務過程、審批流轉、異常處理、統計分析等關鍵環節
- 對需要觸發工作流的自訂動作，必須同步規劃對應的工作流
- 根據業務場景，提供豐富且合理的自訂動作，儘可能簡化使用者高頻操作
- 自訂動作原則：按鈕出現在「操作發起方」的工作表上，而非即將被建立/被操作的目標表上。例：「發起借閱」按鈕在「圖書」表上；「歸還」按鈕在「借閱記錄」表上
- **審批類操作不要拆成自訂動作**。「審批透過」「審批駁回」等操作應由工作流中的審批塊（approve 節點）處理，透過/駁回後的不同邏輯用分支節點區分。正確做法：記錄建立後自動觸發一條包含審批環節的工作流，而非為透過和駁回各建一個按鈕
- 若場景存在行業關鍵規則（如 FIFO、批次追溯、凍結庫存、駁回重提、逾期歸還、部分發貨等），必須體現在方案結構中，而不只是一句描述
- **本階段不展開**：詳細欄位、檢視、圖表設定、工作流節點步驟等細節，這些在後續建置階段補全

### 典型業務場景補齊要求

當場景涉及以下型別時，應自動補足常見控制物件與機制：

- **庫存 / 倉儲類**：倉庫、批次/效期、庫存流水、盤點、調撥、凍結/預留、FIFO/FEFO
- **採購 / 銷售類**：訂單、收發貨、退貨、對賬、結算、供應商/客戶協同
- **借還 / 租賃類**：借出、歸還、逾期、續借/續租、損壞/遺失處理、在借狀態控制
- **審批類**：申請、審批、駁回、撤回、重新提交、審批留痕
- **服務工單類**：受理、分派、處理、回訪、關閉、超時升級
- **專案 / 任務類**：計劃、執行、延期、驗收、變更、風險跟蹤

每個角色包含：名稱 + 1～2 句職責說明 + 主要參與方式。當為外部角色時，名稱後標註（外部）。

## 工作表

每張表包含：**名稱** + 1～2 句說明；當需要自訂動作時，列出動作名稱。

每個頁面包含：**名稱** + 頁面型別（`dashboard` 或 `workspace`）+ 1～2 句說明；標註適用角色。

每條工作流包含：**名稱** + 觸發方式 + 觸發場景與業務目的。
