# niio 應用設計指南

> 本文件覆蓋 niio 應用的**結構設計**（建哪些物件、如何組織）與**內容設計**（欄位、檢視、圖表、工作流、自訂動作的具體規範）。所有設計決策必須嚴格遵循本指南。

---

## 應用命名規範

應用名稱代表整個系統的業務邊界與專業度，應保持極致簡潔、業務場景聚焦、富現代感，並遵循以下原則：

1. **剔除冗餘字尾**：**嚴禁**使用“系統”、“平台”、“軟體”、“工具”、“應用”、“表”、“系統後臺”等傳統而笨重的字尾。
   - ❌ 傳統冗長：`SaaS 客户订阅与服务生命周期管理系统`、`重型设备维保管理平台`
   - ✅ 現代極簡：`SaaS 客户订阅与服务`、`设备维保与健康监测`、`图书借阅大厅`
2. **場景聚焦與字數限制**：應用名稱建議控制在 **2~8 個字** 之間，極其精準地突顯核心業務實體與動作概念本身。

---

## 應用設計順序

設計一個 niio 應用時，應按以下順序推進。每一步都依賴上一步的結論：

| 步驟 | 模組 | 核心問題 |
|------|------|----------|
| 1 | **角色權限** | 誰使用這個應用？各角色職責和權限邊界是什麼？ |
| 2 | **工作表** | 需要管理哪些業務物件？資料模型如何支撐各角色的工作？ |
| 3 | **自動化工作流** | 哪些流程節點可以自動化？哪些需要人工觸發？ |
| 4 | **自訂頁面** | 管理者需要看到什麼資料看板？一線操作者需要什麼工作臺入口？ |
| 5 | **導航分組** | 如何將上述所有內容組織成使用者友好的入口層級？ |
| 6 | **外部門戶** | 是否有外部使用者需要受限訪問？ |
| 7 | **AI 助手** | 是否有明確的智慧查詢或資料分析需求？ |

> **全域原則——以角色驅動設計**：角色是貫穿整個應用的設計主線。每個檢視、自訂頁面、工作流、自訂動作都應先明確“服務於哪個角色”，再決定內容。具體表現為：
> - **檢視**：同一張工作表，不同角色看到不同的檢視（資料範圍、篩選條件、展示欄位各異）
> - **自訂頁面**：不同角色擁有各自的儀表盤或工作臺（管理者看經營分析，操作者看待辦任務）
> - **自訂動作**：按鈕應只對有權操作的角色可見
> - **工作流通知**：通知物件應精確到角色，避免全員廣播

## 一、角色權限（Role）

確定誰使用這個應用，以及他們能看到什麼、操作什麼。角色基於 RBAC 原則設計，用於定義資料範圍、操作權限、審批責任和業務入口。

> **先想清楚「有哪些業務責任」，再決定「需要哪些資料權限」。**
> 角色不是組織架構，也不是崗位名單，而是一組可複用的業務權限能力。niio 支援一個使用者擁有多個角色，因此應優先拆分清晰的業務角色，再透過多角色組合覆蓋複合崗位。

---

### 系統預設角色

系統已包含以下預設角色，**不需要重複建立**：

| 預設角色  | 權限範圍             |
| ----- | ---------------- |
| 應用管理員 | 所有權限（資料 + 應用設定）  |
| 運營者   | 所有資料權限 + 角色/使用者管理 |
| 建置者   | 應用編輯權限（結建置置）     |

設計時只需建立**業務角色**，無需建立「系統管理員」「超級管理員」「平台管理員」等系統級角色。

---

### 角色設計原則

#### 1. 按"業務職責"命名，而非"組織層級"

| 推薦         | 不推薦         | 原因            |
| ---------- | ----------- | ------------- |
| 借閱人員、圖書管理員 | 普通員工、部門成員   | 層級描述，權限邊界不清晰  |
| 採購專員、財務稽核  | 採購部、財務部     | 部門不等於角色       |
| 銷售代表、風控專員  | 業務人員、後臺人員   | 職責過泛，無法指導權限設計 |
| 維修廠、供應商 、讀者   | 外部使用者、外部人員   | 應按外部協作職責命名    |
| ——         | 系統管理員、超級管理員 | 已由系統預設角色覆蓋    |

#### 2. 按"權限差異"決定是否拆分

當角色在以下任一方面存在差異時，就應當拆分為不同角色：

* 能看到的資料範圍不同
* 能操作的工作表不同
* 能執行的動作不同
* 參與的審批節點不同
* 使用的檢視 / 自訂頁面入口不同
* 內部角色與外部角色

#### 3. 利用"多角色組合"，避免建立過度複合角色

niio 支援一個使用者擁有多個角色。不要只按部門或業務域建立“大角色”，例如“銷售”“採購”“財務”等；應根據該業務域下的權限差異，拆分為職責清晰的角色。

如果一個人同時承擔多個職責，應為其分配多個角色，而不是建立一個覆蓋全部權限的複合角色。

| 不推薦 | 推薦 |
|---|---|
| 銷售 | 銷售主管 + 客戶經理 + 一線銷售 |
| 採購 | 採購申請人 + 採購審批人 + 採購執行人 |
| 財務 | 財務稽核人 + 出納 + 費用管理員 |
| 門店 | 門店店長 + 庫存管理員 + 收銀員 |
| 專案 | 專案經理 + 任務負責人 + 專案成員 |

#### 4. 識別外部角色

當業務流程中可能需要**非本組織成員**參與協作時，應設計專門的外部角色。外部角色透過 niio 外部門戶訪問應用，資料天然隔離。

識別訊號：
- 合作方、供應商、客戶、加盟商、外部讀者等需要在系統中填報、檢視或確認資料
- 業務流程中存在"跨組織邊界"的協作環節（如維修廠接單、供應商報價、客戶檢視進度）
- 需要限制資料可見範圍到"僅與自己相關的記錄"
- 當同一角色既有內部協作關係，又有外部協作關係時（如維修廠既有內部管理人員，又有外部維修人員）應設計兩個角色

外部角色預設只能看到與自己關聯的記錄，通常不參與內部審批流程，但可以作為流程的發起方或接收方。

---

### 權限層級參考

| 層級   | 資料範圍                   | 適合角色              |
| ---- | ---------------------- | ----------------- |
| 只讀   | 檢視指定範圍記錄，不能修改          | 管理層、觀察者、彙報物件      |
| 操作員  | 新增、編輯自己負責的記錄           | 一線錄入人員、業務經辦人      |
| 協同處理 | 檢視並處理與自己相關的記錄          | 維修廠、供應商、客服等外部協作方  |
| 主管   | 檢視和編輯團隊或本機構範圍內記錄       | 團隊負責人、設施管理者、部門負責人 |
| 稽核人  | 檢視待稽核記錄，並執行審批、駁回、確認等動作 | 財務稽核、風控專員、法務稽核    |

---

### 完整性檢查

生成業務角色後，按以下清單逐項檢查是否遺漏：

| 角色型別   | 說明                    | 示例                 |
| ------ | --------------------- | ------------------ |
| 一線操作角色 | 負責日常錄入、跟進、處理業務資料      | 銷售代表、諮詢員、倉管人員、維保專員 |
| 業務管理角色 | 負責團隊監督、進度跟蹤、異常處理      | 銷售主管、設施管理者、車隊管理員   |
| 審批稽核角色 | 負責關鍵節點審批、複核、確認        | 財務稽核、風控專員、採購審批人    |
| 專業支援角色 | 負責某類專業業務處理            | 法務專員、評估員、財務專員      |
| 外部協作角色 | 透過門戶或受限入口參與業務（外部角色）   | 維修廠、供應商、客戶、合作機構    |
| 只讀分析角色 | 檢視統計、報表、駕駛艙，不直接操作資料   | 管理層、法人管理者、觀察者      |

不是每個應用都必須包含所有型別，但需要根據業務流程判斷是否需要。注意"管理層"通常應優先作為只讀分析角色，除非其確實參與審批或業務處理。

## 二、工作表（Worksheet）

資料是應用的基礎。工作表設計決定了整個應用的資訊結構。

### 兩類工作表

| 型別 | 特徵 | 典型例子 |
|------|------|----------|
| **基礎資料類**（Master Data）| 主資料，相對穩定，被其他表引用 | 客戶、圖書、裝置、員工、商品 |
| **業務過程類**（Transactional Data）| 流程記錄，隨業務持續產生 | 訂單、申請、借閱記錄、巡檢記錄 |

### 命名準則

- **基礎資料類**：直接用業務物件名（名詞單數）。✅ `图书`、`客户` &emsp; ❌ `图书列表`、`客户信息表`
- **業務過程類**：物件 + 動作名詞。✅ `借阅记录`、`采购申请`、`维修工单`

### 建表判斷

**建表前問自己**：這個物件需要獨立的生命週期管理嗎（需增刪改查）？

- **是** → 獨立建表，透過關聯欄位引用
- **否**（只是分類標籤）→ 用單選 / 多選欄位，不建表

### 核心原則

- **單一資料源**：同一業務物件只建一張表，用欄位區分狀態，用檢視區分角色視角，用權限控制訪問範圍
- **狀態機思維**：業務物件的不同階段是同一張表裡的狀態列位。"待審批"和"已審批"是狀態值，不是兩張表

### 誤用邊界

- 不要按角色拆表——權限差異透過角色設定解決
- 不要把流程階段拆成多張獨立表
- 分類不需要單獨管理時，用單選欄位，不建表

## 三、欄位（Field）

### 系統預設欄位

每張工作表建立時自動包含以下系統欄位，**不需要在設計中額外新增**：

- **建立時間**（ctime）
- **建立者**（caid）
- **最近修改時間**（utime）
- **最近修改人**（uaid）

> 如果業務需要的"建立時間""建立人"語義與上述系統欄位一致，直接複用即可，不要重複建欄位。

### 欄位完整性

設計一張工作表欄位時，按以下 7 個維度依次補齊。**每個維度至少覆蓋 1 個欄位**，不得遺漏任何維度：

| 維度 | 說明 | 典型欄位示例 |
|---|---|---|
| ① 主標識 | 名稱、編號、標題——讓使用者一眼識別這條記錄 | 書名、訂單編號、工單標題 |
| ② 核心業務屬性 | 該業務物件的**核心描述資訊**，體現行業特徵 | ISBN、出版社、頁數、作者（圖書）；規格、品牌、產地（商品）；聯絡人、行業（客戶） |
| ③ 狀態與分類 | 狀態流轉、型別分類、優先順序 | 借閱狀態、圖書分類、緊急程度、審批狀態 |
| ④ 時間維度 | 業務相關的時間節點（系統預設欄位已含建立時間/修改時間，無需重複） | 借出日期、應還日期、截止日期、完成時間、有效期 |
| ⑤ 責任與協作 | 負責人、審批人、操作人（系統預設欄位已含建立者/修改人，無需重複） | 經辦人、管理員、借閱人、審批人 |
| ⑥ 數量與金額 | 數量、金額、統計值——支撐工作流的加減運算 | 庫存數量、單價、總金額、累計次數 |
| ⑦ 說明與憑證 | 備註、附件、圖片、富文字說明 | 圖書封面、備註、合同附件、商品圖片、圖書簡介 |

> ⚠️ **維度 ② 是最容易被忽略的維度**。很多設計只有名稱+狀態+時間，缺少真正體現業務物件特徵的屬性欄位。例如「圖書」表只有書名和作者，缺少 ISBN、出版社、出版日期、頁數、語言、館藏位置等關鍵業務屬性。

### 業務場景欄位補全

根據工作表所屬的業務場景，主動補齊以下常見但容易遺漏的欄位：

**主資料 / 資料類**（客戶、圖書、裝置、商品、員工）：
- 圖片/封面（Attachment）、簡介/描述（RichText）
- 所在位置/地址（Location 或 Text）
- 啟用狀態（SingleSelect 或 Checkbox）
- 行業特徵屬性（如圖書的 ISBN/出版社/页数；商品的規格/品牌/產地；裝置的型號/序列號/購入日期）

**單據 / 記錄類**（訂單、借閱記錄、工單、入庫單）：
- 單據編號（AutoNumber）、操作人（Collaborator）、操作時間（DateTime）
- 處理狀態（SingleSelect，**必須包含完整狀態鏈**，覆蓋從建立到結束的所有狀態）
- 來源/渠道（SingleSelect）

**涉及庫存 / 數量的表**：
- 總量、已用量/在借量、可用量/剩餘量（Number）
- 確保能支撐工作流中的加減運算（如借出時 `可借库存 -1`，歸還時 `可借库存 +1`）

**涉及審批 / 流轉的表**：
- 審批狀態（SingleSelect）、審批人（Collaborator）、審批時間（DateTime）、審批意見（Text）

### 選型規則

* 自由輸入短文字 → `Text`
* 帶格式長文字 → `RichText`
* 普通數值 → `Number`
* 金額 → `Currency`
* 固定單值列舉 → `SingleSelect`
* 固定多值列舉 → `MultipleSelect`
* 選項較多需搜尋 → `Dropdown`
* 只要日期、年、年月 → `Date`
* 要具體時點 → `DateTime`
* 只要時間（不含日期） → `Time`
* 單個是/否 → `Checkbox`（不要用 SingleSelect + 是/否）
* 1～10 級評分 → `Rating`
* 手機號 → `PhoneNumber`
* 座機/電話 → `LandlinePhone`
* 郵箱 → `Email`
* 定位座標 → `Location`
* 省市區行政區域 → `Region`
* 負責人/審批人 → `Collaborator`
* 部門歸屬 → `Department`
* 組織角色 → `OrgRole`
* 跨表引用/聯動/統計 → `Relation`
* 本表父子層級（上級任務/父分類）→ `Relation`（dataSource=selfRelation）
* 數值計算（僅支援+-*/（）數學運算） → `Formula`
* 日期計算/差值/偏移 → `DateFormula`
* 單據流水號 → `AutoNumber`
* 材料/圖片/檔案 → `Attachment`

### 關聯欄位規則

僅在以下情況建立 `Relation`：

* 需要引用另一張表記錄
* 需要與另一張表聯動
* 需要基於另一張表篩選、統計、回寫
* 需要表達本表父子層級

### 誤用邊界

* 狀態、型別、優先順序不要用 `Text`
* 負責人不要用姓名文字，優先用 `Collaborator`
* 不要把所有欄位都做成 `Text`
* 不要僅因"檢視方便"建立關聯
* 不要過度設定必填欄位
* 不要只生成總覽裡提到的幾個欄位就停止

## 四、檢視（View）

### 預設設計規則

每張工作表至少應有 1 個Table 型別的 `全部` 檢視：用於完整瀏覽、篩選、排序、分組、批次處理

根據工作表的業務場景、欄位結構與角色檢視需要，增加 2～5 個其他檢視。

### 檢視排序

先判斷每個檢視的使用頻率和業務作用，再按以下優先順序排列：

1. **主工作入口檢視** — 使用者開啟工作表後最先使用的檢視
2. **待處理 / 高頻操作檢視** — 如 `我的待办`、`待审批`
3. **核心業務推進檢視** — 如狀態看板、專案甘特圖
4. **重要瀏覽輔助檢視** — 如畫廊、日曆、地圖
5. **管理分析檢視** — 如按部門分組、按月統計
6. **`全部` 檢視** — 兜底管理檢視
7. **歸檔 / 取消 / 日誌檢視** — 低頻查閱

不要按檢視型別固定排序；Gallery、Kanban、Calendar、Gantt、Map 如果承擔主工作入口，應直接排第一。例如：
- 圖書表的 `可借图书`（Gallery）、任務表的 `任务看板`（Kanban）、排班表的 `本周排班`（Calendar）
- 專案表的 `项目排期`（Gantt）、網點表的 `网点地图`（Map）

> `全部` 是兜底管理檢視，不要求排第一；但對於**設定表、字典表、日誌表、基礎資料表**等低頻表，`全部` 可以排第一，且可只保留少量必要檢視。

### 欄位、業務驅動的檢視

當工作表的業務和欄位結構與某類檢視高度契合時，**必須**主動新增該型別檢視

| 欄位條件 | 必須新增的檢視 | 說明 |
|---|---|---|
| 存在 selfRelation 或指向本表的 Relation | `Hierarchy` | 天然的父子樹結構，用 Table 無法直觀展示層級 |
| 存在狀態/階段類 SingleSelect（選項 ≥ 3） | `Kanban` | 狀態流轉是看板的核心場景 |
| 存在 Location 定位欄位 | `Map` | 地理分佈只有地圖檢視能直觀呈現 |
| 附件欄位是表的核心內容（如產品圖、案例封面） | `Gallery` | 圖片化瀏覽是 Gallery 的不可替代優勢 |
| 表的業務語義是任務/排期，且有計劃開始+結束日期 | `Gantt` | 專案排期、任務計劃等需要時間軸視角 |
| 表的業務語義是排班/預約，且有時間段+人員/資源欄位 | `Resource` | 資源佔用與時間衝突只有資源檢視能直觀呈現 |
| 表是參數設定/系統設定，通常只有 1 條記錄 | `Detail`（mode=first） | 單記錄場景無需清單，直接展示詳情 |

### 按角色設計檢視

不同角色對同一張工作表的關注點不同，應透過檢視區分角色視角，而非按角色拆表：

* 一線操作者 → 「我的待處理」「我負責的」等篩選型檢視，只看自己相關的資料
* 業務管理者 → 「全部記錄」「團隊待辦」等全域檢視，用於監控和分配
* 審批角色 → 「待我審批」檢視，按審批狀態篩選
* 只讀分析角色 → 按需分配已有檢視的檢視權限即可，通常不需要專屬檢視

### 選型規則

* 批次瀏覽、篩選、編輯、匯出 → `Table`
* 當前人只看自己資料 → 增加篩選型 `Table` 檢視，如 `我的待处理`
* 狀態泳道、拖拽推進 → `Kanban`
* 看某天有什麼 → `Calendar`
* 看任務起止與排期 → `Gantt`
* 看圖片內容（產品、案例、簡歷）→ `Gallery`
* 看單條完整資訊 → `Detail`
* 看父子結構 → `Hierarchy`
* 看地理分佈 → `Map`
* 看資源/人員佔用與排班 → `Resource`

### 誤用邊界

* 有日期欄位，不代表一定建 `Calendar`
* 有開始/結束日期，不代表一定建 `Gantt`
* 有附件欄位，不代表一定建 `Gallery`
* 有關聯欄位，不代表一定建 `Hierarchy`
* 不要因為"要分組"就一律用 `Kanban`，很多場景更適合 `Table + 分组`
* 每張工作表檢視建議不超過 5 個

## 五、自訂動作（Custom Action）

工作表記錄上可以配備操作按鈕（自訂動作），這是串聯業務流程的核心人工入口。

### 三種型別

1. **填寫當前記錄**（`update`）：將一組欄位歸類填寫，方便使用者集中操作。
   > 適用：需要使用者**主動輸入內容**才能推進流程的場景
   > 例：點選「更新圖書資訊」按鈕，彈出表單讓使用者填寫

2. **新建關聯記錄**（`create`）：使用者點選按鈕新建一條關聯記錄
   > 適用：使用者在當前記錄上**發起一件需要填寫資訊的新事務**
   > 例：在「裝置」記錄上點選「報修」按鈕，填寫「報修申請」

3. **直接觸發工作流**（`trigger`）：不彈出表單，點選後直接觸發工作流自動處理
   > 適用：業務推進**不需要使用者輸入**，系統自動完成
   > 例：借閱記錄上的「歸還」按鈕——狀態自動改為已歸還、歸還日期自動寫入今天、庫存自動加一

### 掛載規則

動作必須掛在**動作發起的資料源頭表**上，不要掛在目標表上。

* 發起借閱 → 掛在圖書表，不掛借閱記錄表
* 發起工單 → 掛在客戶表，不掛工單表
* 登記歸還 → 掛在借閱記錄表，不掛圖書表

> 💡 即使不觸發工作流也需要為高頻操作（填寫記錄、新建關聯）儘可能提供自訂動作，提高操作便利性。

### 誤用邊界

* 嚴禁在沒有直接物理關聯（Relation）欄位的兩張表之間，設計並生成型別為 "新建關聯記錄(create)" 的自訂動作。在規劃中定義 `createRelatedRecord` 型別的動作時，**必須同時提供用於物理關聯的具體 Relation 欄位名稱**（該欄位必須顯式宣告在源工作表的 `fields` 清單中）。如果兩張表之間在規劃中沒有直接的 Relation 欄位，則禁止將其規劃為 `createRelatedRecord`，而應當：
  - (1) 在源工作表欄位清單中顯式追加並宣告 Relation 關聯欄位，並在動作中引用它；
  - (2) 或者將自訂動作的型別設計為“直接觸發工作流(trigger)”，利用後臺工作流自動建立對應記錄。
* 不要把"新建關聯記錄"類動作掛在目標表上
* 不要讓需要人工輸入的場景用 `trigger`
* 不要把本可自動完成的動作做成 `update/create`
* 如果欄位值是"今天""當前使用者""固定狀態"等系統可自動確定值，通常不應要求使用者手填
* 不需要人工點選的場景 → 改用自動化工作流，不做自訂動作
* **嚴禁建立「審批透過」「審批駁回」「審批否決」等直接操作審批結果的按鈕**。審批流程的正確設計：使用者點選「提交審批」或「發起審批」按鈕（`triggerWorkflow` 型別動作），或新建記錄時自動觸發（`worksheet_event`），由工作流內部的審批業務塊 (`approval_block`) 流轉——透過/駁回由審批人在審批節點中操作，不是自訂動作按鈕

## 六、自動化工作流（Workflow）

工作流是業務流程的自動化執行，減少重複人工干預。

> **核心原則**：先理清業務流程，再考慮自動化。自動化只是加速，不能替代對流程本身的設計。

### 觸發方式選型

| 觸發方式 | 適用場景 | 典型應用 |
|----------|----------|----------|
| 工作表事件（`RecordEvent`） | 記錄新增 / 編輯 / 刪除後立即觸發 | 通知推送、狀態同步、資料聯動 |
| 日期欄位（`DateField`） | 基於記錄中某日期欄位相對觸發 | 到期提醒、定期跟進、續費預警 |
| 定時（`Scheduled`） | 固定週期執行 | 逾期檢查、週期彙總、盤點提醒 |
| 自訂動作（`CustomAction`） | 使用者主動點選按鈕後觸發 | 審批提交、確認歸還、發起退款 |

### 動作節點選型

* 生成新單據/流水 → 新增記錄 (`add_record`)
* 推進狀態/自動賦值/聯動回寫 → 更新記錄 (`update_record`)
* 刪除特定記錄 → 刪除記錄 (`delete_record`)（⚠️ 僅在必要時使用，優先使用更新狀態為已作廢代替）
* 取得其他表資料 → 查詢單條 (`get_single`) / 多條記錄 (`get_multiple`)
* 對查詢結果統計 → 彙總 (`rollup`)
* 動態計算數值或日期 → 計算 (`compute`)（包含數值公式、日期差值 `dateDiff`、日期偏移 `dateOffset`）
* 觸達相關人員 → 站內通知 (`send_internal_notice`) / 抄送 (`cc`) / 傳送郵件 (`send_email`)
* 流程等待或延遲 → 延時 (`delay`)（支援等待固定時長或延遲到指定時間）
* 引入人工決策與流轉 → 審批業務塊 (`approval_block`)（從發起審批開始，內部可包含審批 `approve`、填寫 `fill_in`、抄送節點）
* 針對多條記錄迴圈執行 → 子流程 (`sub_process`)（常與查詢多條記錄 `get_multiple` 搭配使用，遍歷記錄並逐個處理）
* 按條件分流 → 條件分支 (`branch`)
* 圖形節點不足時補邏輯 → 程式碼塊 (`code`)（支援 JS / Python 指令碼）


### 誤用邊界

* 不要用 `Scheduled` 做即時通知（應使用工作表事件觸發）
* 不要把高頻變化規則寫死在節點裡，優先用欄位值 + 條件分支
* 不要給所有流程都套審批
* 不要只發通知不寫回資料
* 刪除記錄要謹慎，很多場景更適合"更新狀態為已作廢"
* 含有不確定人工判斷的步驟不要自動化，用自訂動作讓人來決策

## 七、統計圖表（Chart）

### 預設設計規則

一個 dashboard 優先覆蓋以下 3 類問題：

1. 核心指標總覽
2. 時間趨勢變化
3. 結構佔比或排行對比

只有業務明確需要時，再補充漏斗、透視、雷達、散點等複雜圖表。

### 選型規則

* 看關鍵數字 → `NumberChart`
* 看完成率 / 達成度 → `GaugeChart` / `ProgressChart`
* 看類別對比 → `ColumnChart` / `BarChart`
* 看名稱較長的類別對比 → `BarChart`
* 看時間趨勢 → `LineChart`
* 看雙指標趨勢 → `DualAxisChart`
* 看佔比構成 → `PieChart`
* 看階段轉化 → `FunnelChart`
* 看排行榜 / TopN → `RankingChart`
* 看雙側群體對比 → `SymmetricBarChart`
* 看多指標綜合比較 → `RadarChart`
* 看兩個數值變數關係 → `ScatterChart`
* 看多維交叉分析 → `PivotTable`
* `Region`欄位 → 看地區分佈（國內） → `RegionMap`
* `Location`欄位 →看地區分佈（全球） → `WorldMap`
* 看文字熱點 / 關鍵詞分佈 → `WordCloud`

### 圖表設計規則

每個圖表都必須先明確：

* 回答什麼業務問題
* 指標是什麼
* 按什麼維度看
* 為什麼值得進 dashboard 首頁

### 誤用邊界

* 不要多個圖表回答同一個問題
* 不要堆過多 `NumberCard` 或 `PieChart`
* `PieChart` 類別過多時改用 `BarChart`
* 沒有明確階段順序不要用 `FunnelChart`
* 沒有連續時間維度不要用 `LineChart`
* 沒有 `Region` 欄位不要用 `RegionMap`，沒有 `Location` 欄位不要用 `WorldMap`
* 每個 dashboard 建議 6~10 個圖表

## 八、自訂頁面（CustomPage）

> **頁面分類**：自訂頁面主要承擔兩種核心角色：
> 1. `dashboard`：以資料統計、趨勢分析為主，聚合工作表資料、展示統計圖表、支撐管理決策。
> 2. `workspace`：以快捷操作、任務處理為主，作為應用的門戶入口、待辦中心或核心業務流的操作檯。

### 設計準則

**先明確頁面目的**：每個自訂頁面應回答一個具體的問題——服務於誰？幫助做什麼？

| 頁面型別 | 服務物件 | 內容側重 |
|----------|----------|----------|
| dashboard | 需要看資料做判斷的角色（管理者、分析者、一線操作者均可） | 趨勢對比、多維交叉分析、聚合統計 |
| workspace | 需要高頻操作的角色（一線操作者、全員） | 當前狀態、待辦處理、高頻操作入口 |

**按角色規劃頁面**：不同角色的關注點和操作方式不同，應為其設計專屬或共享的自訂頁面：

* 管理者/決策者 → 經營分析儀表盤（核心），輔以管理工作臺提供審批、督辦等操作入口
* 一線操作者 → 操作工作臺（核心），輔以業務儀表盤檢視個人績效、待辦統計等資料
* 外部角色（供應商、客戶、維修廠等） → 專屬工作臺（核心且推薦）。外部角色透過外部門戶訪問，工作臺是其最優入口形式——聚合待辦任務、進度檢視、高頻操作（如接單、報價、確認），比直接暴露工作表檢視更安全、體驗更友好。必要時可輔以簡要的業務儀表盤展示與自身相關的統計資料
* 按角色拆分 → 當不同角色關注的指標或操作有差異時，應分別建立獨立的儀表盤或工作臺，而非將所有內容合併到一個頁面。只有當多個角色的關注內容完全一致時，才共享同一頁面

### 頁面元件生態 (Component Ecosystem)

自訂頁面支援多種元件組合，以滿足不同型別頁面的需求：

1. **圖表類 (Chart)**：如 `NumberChart` (數值)、`BarChart` (柱狀圖)、`PieChart` (餅圖)、`LineChart` (折線圖) 等。主要用於聚合展示和分析（`dashboard` 核心）。
2. **操作與資料類**：
   - **快捷按鈕 (Button)**：快捷入口，設定建立記錄/開啟檢視/開啟頁面/開啟連結。
   - **內嵌檢視 (View)**：將工作表的特定檢視（如“待我審批的報銷”、“進行中的專案”）直接嵌入頁面。
   - 主要用於建置工作臺和任務中心（`workspace` 核心）。
3. **展示與佈局類**：
   - **富文字 / 網頁內嵌 (Text / HTML)**：用於展示操作規範說明、規章制度或外部系統連結。
   - **輪播圖 (Carousel)**：以圖片輪播形式展示內容，視覺衝擊力強，適合**展示型、瀏覽型**場景：
     - 推薦/精選/熱門展示（如新書推薦、熱銷商品、精選案例、優秀員工）
     - 公告/通知/活動輪播
     - 品牌宣傳、活動海報
     - 重點專案/成果展示
   - **標題區 (Section)**：用於頁面的視覺分割槽。

> 💡 **View vs Carousel 選型**：使用者需要篩選/操作資料 → View；只需瀏覽瞭解（推薦、公告、展示） → Carousel。

### 誤用邊界

- 不要混淆元件型別定位（如在 workspace 堆砌大量折線圖，或在 dashboard 放置過多操作按鈕）
- 不同頁面應有明確的分工，不重複展示相同資料或入口
- 不要把展示型推薦內容（如"新書推薦""熱門商品"）做成內嵌檢視，應使用輪播圖

## 九、導航分組（Navigation Group）

導航結構決定使用者進入應用後的第一印象和操作路徑。

> **核心原則**：以使用者的業務任務和使用場景為主線組織導航分組，兼顧核心業務物件，確保入口清晰、層級穩定、路徑自然。

### 推薦結構（從上到下）

| 分組位置 | 推薦內容 | 說明 |
|----------|----------|------|
| 1. 總覽 / 首頁 | 自訂頁面（Dashboard / Workspace）、AI 助手 | 讓使用者一眼掌握全域狀態和核心待辦 |
| 2. 核心業務 | 高頻操作工作表 | 借閱管理、訂單處理、工單跟進 |
| 3. 基礎資料 | 主資料工作表 | 低頻使用，放靠後 |
| 4. 設定與管理 | 分類維護表、基礎資料表 | 極低頻，由管理員維護 |

### 分組命名準則

- 優先使用簡潔的業務場景詞命名；如：借閱 優於 借閱管理，裝置 優於 裝置運維
- 組名 2～4 字，應簡潔、明確
- 同層級分組名稱應保持一致的抽象維度

### 結構約束

- 分組通常控制在 3～5 個，避免首層分組過多
- 每組通常承載 2～5 個專案
- 禁止單項分組，只有 1 項時併入相鄰分組
- 自訂頁面優先歸入"總覽"或對應業務分組

## 十、AI 助手（AI Assistant）

基於應用內資料提供智慧問答、資料查詢和分析建議。

### 適用場景

| 適合 | 不適合 |
|------|--------|
| 資料查詢："本月庫存還剩多少？" | 替代工作流執行自動化操作 |
| 狀態查詢："我的申請審批到哪步了？" | 代替人工完成介面操作 |
| 輔助分析："哪類圖書借閱量最高？" | — |

> 僅在有明確查詢或分析需求時規劃，不強制每個應用設定。

## 跨模組閉環設計

應用設計中，檢視、欄位、工作流、自訂動作之間存在強依賴關係。任何一環缺失都會導致功能無效。設計時必須確保以下閉環完整。

### 1. 工作流資料閉環

每條工作流優先形成以下閉環：

1. 更新主表狀態
2. 更新關聯表統計或狀態
3. 新增流水/日誌
4. 傳送通知

若只有通知、沒有資料寫回或留痕，通常閉環不足。

### 2. 檢視 ↔ 欄位閉環

檢視的篩選條件必須有對應的欄位和選項值支撐。

* ✅ 正確：規劃了“超期事項(Table)”檢視，狀態列位包含“已超期”選項：`"事项状态(SingleSelect:待分解/办理中/已完成/已超期/已归档)"`
* ❌ 錯誤：規劃了“超期事項”檢視，但狀態列位只有 `"事项状态(SingleSelect:待分解/办理中/已完成/已归档)"`——缺少“已超期”選項，檢視無法篩選

### 3. 欄位 ↔ 工作流閉環（時效性狀態）

當狀態列位中存在系統自動判定的選項（如“已超期”“已逾期”“已過期”），該選項無法由使用者手動設定，必須有對應的工作流自動標記。

* ✅ 正確：狀態列位有“已超期”選項，同時規劃了一條 `date_field` 觸發的工作流：“完成時限到達時，若事項狀態不是已完成，則自動更新為已超期並通知責任人”
* ❌ 錯誤：狀態列位有“已超期”選項，但沒有任何工作流來自動標記——該選項永遠不會被設定，檢視始終為空

典型實現模式：
* `date_field` 觸發 → 完成時限到達時，檢查是否已完成，若未完成則更新狀態為“已超期”
* `schedule` 定時觸發 → 每日檢查所有未完成記錄，將超過完成時限的標記為“已超期”

### 4. 自訂動作 ↔ 欄位 ↔ 工作流閉環

自訂動作的前置條件和執行結果都必須有欄位支撐，狀態變更必須有工作流執行。

* ✅ 正確：“歸檔”按鈕的啟用條件為“事項狀態=已完成”，點選後觸發工作流將狀態更新為“已歸檔”
* ❌ 錯誤：“歸檔”按鈕沒有設定啟用條件，任何狀態下都可以點選歸檔，導致未完成的事項也可被歸檔

### 5. 自訂頁面 ↔ 檢視 / 欄位閉環

工作臺中內嵌的檢視元件和儀表盤中的圖表都依賴工作表欄位的完整性。

* ✅ 正確：儀表盤中“超期事項數(NumberChart)”指向事項表，篩選條件為“狀態=已超期”，欄位和工作流均已配套
* ❌ 錯誤：儀表盤有“超期事項數”圖表，但狀態列位沒有“已超期”選項，也沒有工作流標記超期——圖表始終顯示 0

地圖圖表的欄位閉環：
* `RegionMap`（國內地區分佈）→ 工作表必須有 `Region` 型別欄位

* ❌ 工作表無 `Region` / `Location` 欄位時，禁止規劃地圖類圖表
