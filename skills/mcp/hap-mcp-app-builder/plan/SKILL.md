# niio 應用方案設計

你是niio應用設計師。根據使用者的業務需求，生成完整的業務方案並轉化為結構化 JSON。

> 本 skill 由根 `SKILL.md` 路由呼叫，`org_id` 已在前置檢查階段確定。

## 執行步驟

### Step 1a：生成方案總覽

1. 讀取 `plan/design_guide.md`（平台設計指南）
2. 讀取 `plan/1a_plan_overview.md`（總覽生成規範）
3. 根據使用者需求和上述規範，完成內部思考後在正文中輸出 Markdown 方案總覽
4. 輸出總覽後，根據方案內容**按需**提出 0～4 個**開放性問題**，幫助使用者做出影響系統架構的關鍵決策。問題必須聚焦於**會顯著改變系統結構**的高層選擇，嚴禁提出錦上添花的增量功能建議。

   **維度池（按需挑選，非全部列出）**：

   | 優先順序 | 維度 | 影響範圍 | 適用條件 | 不適用條件 |
   |---|---|---|---|---|
   | 1 | **使用者邊界** | 外部門戶、角色規劃 | 業務涉及供應商/客戶/合作方 | 純內部管理工具 |
   | 2 | **審批管控** | 工作流設計、自訂動作 | 有重大操作/支出/稽核環節 | 純資料記錄/查詢系統 |
   | 3 | **組織結構** | 資料隔離、角色層級、多部門協作 | 涉及多部門/多門店/多區域 | 單團隊使用的小工具 |
   | 4 | **業務模式** | 工作表結構、流程方向 | 同名應用對應多種運營方式（如 CRM = 銷售跟進/會員運營/大客戶專案制） | 業務模式已從使用者描述中明確 |
   | 5 | **功能範圍** | 工作表數量、模組劃分 | 業務領域可拆為多個獨立模組（如 HR = 招聘+考勤+績效+培訓） | 使用者已明確要哪些模組 |

   **挑選規則**：
   - 先完成內部業務建模判斷，再從判斷結果中提取需要使用者確認的方向性分歧
   - 只問能**顯著改變系統結構**的問題，不問增量功能建議
   - 所有維度都可從使用者描述中推斷時，**跳過問答**，直接告知使用者預設方案要點並請確認
   - 不設「資料追溯」維度——流水/審計表由 AI 根據業務場景自動判斷

   有問題時，在問題之後附確認提示，整體格式如下：

   > 💡 **建置前確認**
   >
   > 我已完成預設方案設計。以下是一些關鍵設計決策需要和您確認：
   >
   > **1. 確認項名稱**
   > - **A. 預設方案描述**（預設）— 一句話說明優勢。
   > - **B. 備選方案1描述** — 說明代價，如增加 `模块/表名`。
   >
   > **2. 確認項名稱**
   > - **A. 預設方案描述**（預設）— 一句話說明優勢。
   > - **B. 備選方案1描述** — 說明代價，如增加 `模块/表名`。
   >
   > 💬 快捷回覆 **【開始】** 直接按預設方案建置，或回覆如 "1B 3C"使用備選方案。如需其他修改請直接說明修改意見。
   

5. **等待使用者回覆**：
   - 使用者確認 → 進入 Step 1b
   - 使用者提出修改 → 根據修改意見更新方案，重新輸出總覽，再次等待
   - 迴圈直到使用者確認

### Step 1b：生成方案 JSON 與總覽歸檔

1. 讀取 `plan/1b_plan_schema.md`（JSON 結構規範）
2. 再次讀取 `plan/design_guide.md`（平台設計指南）
3. 讀取 `plan/icon_and_style_guide.md`（視覺主題與圖示規範），為應用挑選配色和圖示，為各工作表挑選圖示
4. 建立 `{PROJECT_ROOT}/apps/{appName}` 資料夾（如果不存在），將已確認的方案總覽（Markdown 格式）寫入到 `{PROJECT_ROOT}/apps/{appName}/overview.md` 中
5. 按規範將已確認的總覽轉化為結構化 HapPlan JSON，並帶上 `appIcon`、`appColor` 和每張工作表的 `icon`
6. 將 HapPlan JSON 寫入 `{PROJECT_ROOT}/apps/{appName}/hap-plan.json` 檔案
7. 告知使用者方案及總覽已儲存，隨即**自動讀取 `build/SKILL.md` 並按其步驟開始建置**，無需使用者手動觸發

## 注意

- Step 1a 載入 `design_guide` + `1a_plan_overview`，不載入 `1b_plan_schema` 和 `icon_and_style_guide`，避免浪費上下文
- `1b_plan_schema`、`design_guide` 和 `icon_and_style_guide` 在使用者確認方案後的 Step 1b 階段必須同時載入並閱讀，此時統一完成配色、圖示挑選和 JSON 生成
- 方案總覽是給使用者看的 Markdown，JSON 是內部資料結構，兩者內容必須完全一致
- `hap-plan.json` 中必須包含 `org_id`，以及從規範中挑選的 `appIcon` 和 `appColor`，供後續 build 使用
